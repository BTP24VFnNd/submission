You are an expert software engineer and security analyst.

Analyze the following code for security vulnerabilities.

Use Structured Chain-of-Thought (SCoT): reason using explicit program structures:
- Sequence (ordered steps)
- Branch (if/else)
- Loop (for/while)

Four disciplines apply to EVERY step below:

1. GUARD ANCHORING: a check, bound, or invariant exists ONLY if you can QUOTE the exact statement from the given code that enforces it, and only if that statement constrains the exact variable, in the exact unit, with the exact operator the sink requires (`>` vs `>=`, `<` vs `<=`, the compared length vs the copied length, the checked index vs the used index). A guard is ANY statement that provably keeps the consumed value inside its required domain: a bounds/range/NULL/emptiness check, a clamp, a mask or modulo bounding the value (`& 0x7f`, `% n`), a narrowing cast whose target width provably contains every value the producing expression can reach (compute that maximum, do not assume it), an error arm that returns/breaks/continues before the sink, an allocation sized from the same expression as the copy length, a loop bound that caps iterations, or a fully-enumerated switch whose default arm rejects. Contracts with callers or not-shown callees ("the caller never passes NULL", "the decoder masks the field") are assumptions unless quotable; an unquotable contract can never dismiss a candidate AND can never serve as a guard. Judge this code as the last line of defense.

2. GUARD ARITHMETIC (verify, never assert): every guarded code and every defective code you will see is one variant of a near-identical pair — the safe twin differs from the vulnerable twin by one small guard, or by one operator/units detail inside an otherwise identical check. Therefore, for every candidate AND for every guard you dismiss, do the arithmetic: take the candidate's concrete boundary value (0, -1, empty, exactly-at-limit, one-past-limit, min/max of the declared width, wrap point), apply it to the quoted check, and compute the result. A guard you found but did not execute against the attack value is unverified; a guard you declared absent without a line-by-line scan is unsearched. If the code contains ANY validation of the same variable near the sink — a length check, a containment/prefix test, a NULL test, a clamp, a loop bound — treat it as the decisive statement and verify its operator and unit at BOTH bounds before calling it sufficient or insufficient: the difference between safe and vulnerable is usually one more or fewer unit, operator, or ordering detail inside exactly this check, not the presence of an entirely different construct.

3. IMPACT MODEL: direct security impacts are memory corruption (out-of-bounds write, attacker-controlled format string, uninitialized value reaching control flow or output), out-of-bounds read, injection, authn/authz/verification bypass, fail-open security state (presenting secure/verified/authorized on an unverified or error path), and attacker-scalable resource consumption. OUTPUT-CONSTRUCTION RULE: when a statement builds a URL, log line, HTTP header, HTML, SQL/XPath query, shell command, or file path from attacker-influenced content without the validation or encoding that context requires, the CONSTRUCTION itself is the vulnerability (CWE-918/117/113/79/89/943/78/22 respectively) — do NOT demote it because the downstream consumer of the output is not shown; the tainted output is itself the impact (request forgery, log forging, header splitting, markup injection, query injection). Memory-corruption candidates, in contrast, must have every link of the chain quoted in this code or characterizable from standard-function semantics (memcpy copies exactly n bytes; strcpy/strcat copy up to the source NUL; allocation functions return NULL on failure; lookups/parses can miss and return a failure sentinel — NULL, negative, end-iterator — that this code must test before first use). A NULL dereference that merely crashes the same-privilege process that supplied the input, with no corruption, disclosure, bypass, or amplification, is a robustness issue → notes.limitations, never the verdict. An unbounded-input defect in code that parses untrusted data is real regardless of how "typical" inputs look.

4. ATTACKER AND WIDTH-DOMAIN MODEL: an attacker is anyone across a trust boundary — a network peer, the originator of a parsed file/message/packet, a guest VM or untrusted device whose register/DMA values this code consumes (guest-induced host corruption is corruption, not an "emulation accuracy issue"), an unprivileged user reaching a higher-privileged process, and any data-carrying parameter of a non-static, exported, callback, protocol, or handler function (handle_*, *_write, *_read, *_decode, *_parse, *_ioctl, on_*, callbacks, overridden virtuals). For any value whose producer is not shown in this code (parameter, callee return, global, struct field set elsewhere), the input surface is the FULL domain of its declared type/width — any representable value is instantiable, and "the producer probably narrows it" is an unquoted assumption that can never block a trigger. The absent local validation at the use IS the defect: a call passing an attacker-derived raw offset/size/index/pointer into a memory, copy, or indexing operation is defective AT the call site even if the crash lands inside the callee; a callee return consumed without a local sentinel check is defective at the unchecked use.

Perform the following SCoT procedure, writing each step with numbered program-structure labels:

STEP 1 — SEQUENCE: Input and trust-boundary inventory.
Enumerate every input this code consumes (parameters, callee returns, parsed data, globals, device/register state, callback-observed fields). Branch on each: attacker-data (content, size, index, offset, name, path, token, key from across a trust boundary; surface = declared width) vs. contract (ONLY if this code itself documents, asserts, or checks the precondition — quote it; otherwise classify as attacker-data) vs. internal-trusted. Record for each: entry line, declared type/width and its full domain, verdict. THEN a mandatory re-check: IF nothing was classified attacker-data, re-examine every parameter and callee return for the intake-point shapes of discipline 4 before concluding "no attacker-data".

STEP 2 — LOOP: Taint trace with per-sink mention sweep.
For each attacker-data input, follow every path through assignments, arithmetic, casts, container writes, and pointer arithmetic to every sink: memory access/indexing, allocation sizing, copy/memset/string lengths, pointer scaling, format strings, command/shell, SQL/XPath, file paths, HTML/log/header assembly, outbound URL/host/port, crypto key/nonce generation and signature/MAC verification, authz decisions, loop bounds, free/delete, call sites passing attacker-derived sizes/indices/offsets/pointers/strings to any callee, and arithmetic consuming callee returns (e.g. `remaining -= count`). At each sink, state the required precondition (bounds, non-NULL, termination, canonical form), then run the MENTION SWEEP: list, in code order, EVERY statement mentioning the tainted variable, its aliases, and the bound it must respect; branch each mention guard / not-a-guard with a one-clause reason. IF a guard exists in the enumeration: QUOTE it, verify per disciplines 1-2 (all guard forms, computed maximum, both operator directions), and verify its position in EXECUTION order, not textual order — a guard bypassed by a `continue`/`break`/early return/branch, skipped by one loop branch, or placed after the first use does not protect the sink; for loop-carried values decide per iteration whether the FIRST use of each iteration is covered. Watch specifically for: `>` where `>=` is required, unsigned wrap inside the guard's own arithmetic, a check on a different variable or in the wrong unit, and a sentinel check arriving after the first use. ELSE record the candidate, quoting any statement whose own data flow can produce the harmful value (unchecked allocation, missed lookup/parse, wrapping subtraction).

STEP 3 — LOOP: Candidate generation.
Collect STEP 2 candidates plus any other defect: integer overflow/underflow/truncation (CWE-190/191), off-by-one and boundary operator errors in BOTH directions, signedness and width confusion, buffer size miscalculation (CWE-131), incorrect pointer scaling (CWE-468), dangerous functions (CWE-676: memcpy, sprintf, strcpy, gets, popen, rand used for security), improper null termination (CWE-170), uninitialized values reaching a use (CWE-457/CWE-908), UAF/double-free (CWE-416), race conditions, fail-open logic and authz gaps (CWE-862/863), security-state misrepresentation (CWE-451), missing signature/MAC/certificate verification (CWE-347), weak primitives or key sizes (CWE-326/327), predictable salt (CWE-760), insufficient randomness (CWE-330/338), insecure temporary files (CWE-377), uncontrolled resource consumption (CWE-400, ReDoS CWE-1333), and output/injection construction per discipline 3 (command CWE-78, SQL CWE-89, XPath CWE-943, XSS CWE-79, format CWE-134, log CWE-117, header CWE-113, path CWE-22, open redirect CWE-601, SSRF CWE-918).

STEP 4 — BRANCH: Trigger proof by step-by-step simulation.
For each candidate, walk the code in order writing the concrete runtime value of every relevant variable from the trigger input to the defective statement, and through every link of the claimed impact. A trigger precondition is instantiated when it is (i) any value representable in the declared width of attacker-data per discipline 4, (ii) a standard failure sentinel per discipline 3 (NULL from malloc, a missed lookup, a negative parse result — always in-domain), or (iii) a state a quoted statement of this code produces. Branch:
- IF the simulation reaches the defective statement with all values concrete, every impact link is a quoted statement here or a characterizable callee per discipline 3, and the consequence is a security impact per discipline 3 — including the OUTPUT-CONSTRUCTION RULE — the candidate is a real vulnerability in this code.
- SINGLE-ANOMALY RULE: exactly one concrete anomaly (one wrong comparison operator, one unchecked sentinel, one missing bounds test at a security-relevant use of attacker-data) is the defect unless a QUOTED guard from the STEP 2 sweep neutralizes it; it may not be demoted by an unquoted contract, an unshown callee, or an impact argument resting on code not given.
- OFF-BY-ONE RULE: a wrong-direction comparison consuming attacker-data is real if ANY bound under-admits (one-past-the-limit, minimum, maximum, or wrap point passes); only if the operator provably over-rejects at one bound AND cannot under-admit at any other bound of the same or mirrored check may you record it as functional over-rejection in notes.limitations.
- ELSE IF the trigger needs a caller/callee violating a precondition this code does not quote, an unexhibited race window, a wrap at a scale an earlier quoted check bounds below, or an attacker-planted filesystem object at a path this code's statements never make attacker-writable — it is SPECULATIVE → notes.limitations, naming the precondition you could not instantiate.
- ELSE IF the impact requires an unshown step outside this code BEYOND the output-construction rule — a later stage that "might" misuse a value, a consumer whose behavior is not shown, a deployment assumption — the impact is NOT instantiated → notes.limitations.
- Never demote what discipline 3 names as direct impact; never PROMOTE a candidate whose chain breaks at a link that is neither quoted here nor characterizable per discipline 3.

STEP 5 — BRANCH: Patch hunt, then re-examination of dismissals.
LOOP over each surviving candidate: state in words the minimal one-line guard that would fix it. Enumerate the forms that fix can take: bounds/NULL/range/emptiness/length check, clamp, mask or modulo bounding the value, corrected comparison operator or loop bound, resized or reallocated buffer, allocation sized from the same expression as the copy, checked accessor or bounds-safe helper, rejecting default/error arm, failure-sentinel test before first use, safe-truncating call. LOOP over the given code, line by line, in code order, searching for EVERY one of those forms on EVERY path to the sink — the STEP 2 mention sweep is your checklist. IF you find one, quote it and RE-SIMULATE the candidate's concrete attack value through it per discipline 2: IF the quoted guard provably blocks that exact value in execution order, the candidate is NOT real — you misread the code. Only when you can name the ONE guard whose absence is the defect and prove it appears nowhere in the sweep may you confirm.
LOOP over each candidate you are about to dismiss, and branch on the dismissal reason:
- "the caller / external component / decode layer is responsible": INVALID if this code is the intake point (it parses the file, decodes the message, receives the guest command, implements the public API) — missing validation IS the vulnerability; do not defer it.
- "bounded by construction / by the framework / by code not shown": INVALID per discipline 1 and the width-domain rule — restore the candidate and simulate.
- "no caller is visible / reachability unprovable": judge by the values consumed — run STEP 4 on attacker-data parameters; "constraints are applied at the decode site (not shown)" is never a valid dismissal.
- "thin wrapper, defect is in the callee not shown": the defect is HERE if this code passes an out-of-domain argument (raw offset, unchecked size, unvalidated index/pointer) or consumes a return without a sentinel check; dismiss only when the harmful use occurs entirely inside the not-shown callee AND the in-domain claim rests on a quoted contract.
- "only a logic/UI/cosmetic issue": INVALID for fail-open defaults, error paths that let unvalidated values through, authorization gaps, and security indicators presenting the secure/verified state on an unverified or error path — those ARE vulnerabilities; "cosmetic" means non-security output only.
- "worst case is a crash": valid ONLY under discipline 3's same-privilege rule and only when the trigger is speculative under STEP 4; a crash of a shared or higher-privileged process induced by a lower-privileged party's data is at least denial of service, and a memory-corruption primitive is never "only a crash".

STEP 6 — LOOP: Short-snippet sweep (run ONLY if no primary candidate survived).
LOOP over every statement in the given code in order (full sweep when the code is under ~50 lines; for longer code sweep only the statements STEP 2 marked as sinks or sentinel-consuming uses). For each statement, BRANCH: assume this single statement IS the vulnerable line — what attacker-data value makes it fail (wrong result, out-of-bounds access, NULL deref, wrap, missing sentinel check), is that value within the declared width domain per STEP 1, and does any quoted guard on any path prevent it? IF you find one whose failing input is attacker-data and whose guard is absent per the STEP 5 search, promote it and run STEP 4 on it. IF after the sweep every statement is defensible, the verdict is not vulnerable.

STEP 7 — SEQUENCE: Verdict reduction, CWE, and localization.
- Reduce the verdict to ONE named guard: quote the single decisive statement — either the statement that provably blocks the only surviving trigger (→ not vulnerable) or the reachable sink that no statement anywhere in the code prevents (→ vulnerable). Only PRIMARY candidates (trigger fully instantiated in STEP 4, every impact link quoted or characterizable) may decide the verdict, appear in evidence, or drive the CWE; a single surviving primary candidate suffices. Speculative candidates never flip the verdict.
- CWE: emit exactly ONE CWE unless you can name TWO independent primary defects, each with its own quoted trigger — a consequence class, a second guess, or another view of the same defect does NOT qualify; one correct CWE beats two. Derive it from the quoted sink of the primary defect, root cause before consequence: out-of-bounds write → CWE-787; out-of-bounds read → CWE-125; integer overflow → CWE-190; underflow/sign → CWE-191; UAF → CWE-416; NULL dereference → CWE-476; division by zero → CWE-369; CWE-120 when the overflow flows through a classic dangerous string/copy function; CWE-119 only when no primitive applies; CWE-676 only when the mere use of the dangerous function is the defect. When the primary defect is an output-construction or validation defect, name ITS class, never a memory primitive: SQL query against a database API (SELECT/INSERT/WHERE) → CWE-89; XPath expression (axes, predicates, //node) → CWE-943 — never interchange them; markup destined for HTML rendering → CWE-79; outbound request whose URL/host/port the attacker controls → CWE-918 (never CWE-20; CWE-601 only when the value lands in a redirect/Location header); attacker-controlled format string → CWE-134; log forging → CWE-117; HTTP response/header splitting → CWE-113; path escape → CWE-22; shell command → CWE-78; buffer not NUL-terminated before a string function → CWE-170 first, CWE-120 second; buffer size miscalculation → CWE-131; pointer scaling → CWE-468; missing authorization → CWE-862/863; incorrect file permissions → CWE-732; security-state misrepresentation → CWE-451; missing signature/MAC verification → CWE-347; predictable salt → CWE-760; weak randomness → CWE-330/338; broken primitive → CWE-327; insufficient key size → CWE-326; insecure temp file → CWE-377; ReDoS → CWE-1333; other unbounded consumption → CWE-400. Use CWE-20 only when no more specific class names the defect. Never pad with consequence CWEs or hardening advice.
- Localization: for each confirmed finding, emit one evidence entry whose location is the narrowest contiguous range covering the faulty statement — the sink, the unvalidated use, the wrapping subtraction, or the missing-check site — anchored on the defective line, typically 1-4 lines; never widen the range to include surrounding context. If the tainted value originates in a distant statement, add ONE additional evidence entry anchored on that origin line. start_line and end_line must be concrete integers, never null, and the snippet must be copied verbatim from those lines. Then RECOUNT: treat the first line of the given code as line 1, count down to your range, and verify the snippet appears at exactly those lines; if the recount disagrees, correct the numbers before emitting JSON. Every evidence entry must map to a surviving primary candidate.
- Confidence: set by verification strength, not feeling. High (0.85-1.0) only when the mention sweep verified the guard's absence AND the trigger and every impact link were simulated with quoted statements; moderate (0.6-0.85) when the finding rests on any remaining unquoted assumption; lower when the reasoning leans on context you inferred rather than quoted.

OUTPUT BUDGET (mandatory): keep the ENTIRE SCoT reasoning compact — at most 40 lines, or at most half the code's length for code over ~100 lines; one line per input, per sink, per candidate; batch similar candidates into one simulation. The JSON object is the deliverable: when space runs short, cut reasoning detail, never the JSON. The final JSON must contain ALL THREE top-level keys — "verdict", "evidence", "notes" — with notes.assumptions and notes.limitations present even when empty. An omitted key or a truncated JSON invalidates the analysis as surely as a wrong verdict.

Output format requirements:
- First: write your SCoT reasoning in plain text with numbered steps (STEP 1 through STEP 7), labeling sequences, branches, and loops explicitly, and quoting the exact code lines whenever you claim a guard exists or a defect is present. In STEP 2 show the mention sweep for each sink you call unguarded; in STEP 4 show the simulated runtime values; in STEP 5 list the fix forms you searched for and quote any guard that blocks the attack value; in STEP 7 state the single named guard the verdict reduces to.
- Then: output exactly one JSON object (no markdown fences, no extra text before or after it). It must be strictly valid: no trailing commas, no comments, every field present — "evidence" and "notes" must appear even when their arrays are empty.
